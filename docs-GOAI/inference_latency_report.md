> 测量日期：2026-09-19 ｜ 机器：L20（NVIDIA L20 46 GB）｜ 数据源：`~/goai-trace/`

> 因此下面所有 `ns=20` 的数字都是该时刻的快照。口径与排除规则见 §6，**读数字前请先看那一节**。

## 1. 结论摘要

**单次模型推理**（服务端 `infer()` 全程，不含网络）：

| `num_steps` | 样本 | 中位 | 均值 | p95 | 范围 |
|---|---|---|---|---|---|
| 50 | 639 帧 | **666.8 ms** | 667.1 | 677.6 | 649.3 – 736.6 |
| **20** | 1674 帧 | **311.0 ms** | 312.2 | 322.8 | 302.3 – 341.3 |

**整个 loop 间隔**（上一次 `get_action` 完成 → 下一次完成，含动作播放）：

| `num_steps` | 样本 | 中位 | 均值 | p95 |
|---|---|---|---|---|
| 50 | 623 | **1562 ms** | 1578 | 1609 |
| **20** | 1649 | **1205 ms** | 1689 | 2678 |

> `num_steps=20` 那一组的**均值被 75 次中途停顿（≥3 s）拉高**，看中位数更准。详见 §5。

**三段拆解**（取「正常 loop」即 <3 s 的中位数）：

| 组成 | `num_steps=50` | `num_steps=20` | 说明 |
|---|---|---|---|
| **模型推理** | 667 ms (42.7%) | **311 ms (25.8%)** | 服务端实测 |
| **动作播放** | 640 ms (41.0%) | **640 ms (53.2%)** | 16 步 × 40 ms（按协议标称值推导） |
| **传输 / 协议** | 255 ms (16.3%) | **253 ms (21.0%)** | loop − 推理 − 播放 |
| **合计** | 1562 ms | **1204 ms** | |

**两个关键结论：**

1. **推理只占 loop 的四分之一**（`num_steps=20` 时）。把 `num_steps` 从 50 降到 20 让推理砍掉 53%，但 loop 只降了 23% —— 因为播放和传输这两块**完全没动**，现在合起来占 74%。
2. **非推理开销稳定在 ~254 ms**，且**与 `num_steps` 无关**（255 vs 253）。这个稳定性说明拆解是可信的 —— 剩下要优化的就是这 254 ms 和 640 ms 播放。

## 2. 模型推理耗时

### 2.1 分阶段

| 阶段 | `num_steps=50` 中位 | 占比 | `num_steps=20` 中位 | 占比 |
|---|---|---|---|---|
| `prepare_ms` 观测准备（含 tokenizer） | 8.5 ms | 1.3% | 8.3 ms | 2.7% |
| **`denoise_ms` 去噪循环** | **658.0 ms** | **98.7%** | **302.5 ms** | **97.3%** |
| `decode_ms` 反归一化 + delta + 裁剪 | 0.2 ms | 0.03% | 0.2 ms | 0.06% |
| `wall_ms` 合计（调用点实测） | 666.8 ms | 100% | 311.0 ms | 100% |

**推理耗时几乎 100% 是去噪循环。** 观测准备只有 8 ms，输出解码 0.2 ms —— 这两个方向不值得优化。

### 2.2 去噪步数的线性模型

用两组中位数拟合：

```
推理耗时(ms) ≈ 73.9 + 11.86 × num_steps
```

| `num_steps` | 预测 | 实测 |
|---|---|---|
| 50 | 667 ms | 666.8 ms ✓ |
| 20 | 311 ms | 311.0 ms ✓ |
| 10 | 192 ms | — |
| 5 | 133 ms | — |

每步去噪实测：`ns=50` 为 13.16 ms/步，`ns=20` 为 15.13 ms/步 —— 不完全线性，有约 74 ms 的固定开销（prefix 前向 + KV cache）。

### 2.3 稳定性

`num_steps=20` 那组 1674 帧的范围是 **302.3 – 341.3 ms**（±6%），p95 仅 322.8 ms。**推理耗时非常稳定**，没有长尾 —— 说明不是推理在造成卡顿。

## 3. Loop 间隔

### 3.1 定义

服务端两次相邻 `get_action` 完成时刻之差。客户端官方循环是：

```
while not end:
    obs = get_obs();  update_obs(obs)
    actions = get_action()          ← 服务端在此记 t
    for action in actions:
        take_action(action)          ← 播放（40 ms/步）
        obs = get_obs(); update_obs(obs)
```

所以两次 `t` 之间 = **播放 N 步 + 中间 N 次 `update_obs` 往返 + 下一次推理**。

**这不是推理耗时。** 两者差着播放与传输，必须分开看。

### 3.2 客户端确实执行完整 chunk（实测依据）

在同 episode 内的 911 组相邻帧上比对「下一帧的 state」与「上一帧 action 的第 k 步」：

| 对比 | 平均差 |
|---|---|
| `action[i][0]` | 0.04723 rad |
| `action[i][4]` | 0.03491 rad |
| `action[i][8]` | 0.02216 rad |
| `action[i][12]` | 0.00891 rad |
| **`action[i][15]`** | **0.00886 rad** ← 最接近 |

单调收敛到第 15 步，且实测帧间 state 位移 0.0548 rad ≈ 16 步累计 0.0620 rad。
**结论：客户端把 16 步全部执行完才请求下一个 chunk，播放时间确实在 loop 间隔内。**

## 4. 拆解与瓶颈归属

### 4.1 三段分解

```
num_steps=50 :  1562 ms = 推理 667 + 播放 640 + 传输 255
num_steps=20 :  1204 ms = 推理 311 + 播放 640 + 传输 253
                              ↑ 唯一变化的一项
```

播放 640 ms 来自协议标称值（40 ms/步 × 16 步，见 `INTERFACE.md`「nominal data interval is 0.04 s」）。

**传输那一项在两组里是 255 vs 253 ms —— 几乎完全相同。** 这是拆解正确的强证据：`num_steps` 不该影响传输，而实测也不影响。

### 4.2 优化空间排序

| 项 | 当前 | 可压缩到 | 手段 | 证据强度 |
|---|---|---|---|---|
| **播放** | 640 ms (53%) | ~490 ms | `execution_horizon` 16→8 后重规划更频、或动作压缩 | 播放时长由步数×步长决定，非推理可改 |
| **传输/协议** | 254 ms (21%) | 未知 | 查 `update_obs` 的图像编码格式 | **待测**，见 §5.3 |
| **推理** | 311 ms (26%) | ~192 ms | `num_steps` 20→10 | 已实测线性模型 |

## 5. 异常与注意事项

### 5.1 中途停顿

`num_steps=20` 的 1649 个 loop 里有 **75 个 ≥3 s（4.5%）**，最长 **54.8 s**。这些是 episode 中途的操作停顿（操作员干预 / 场景复位 / 网络中断），不是正常 loop。剔除后正常 loop 中位 **1204 ms**（n=1574）。

`num_steps=50` 那组只有 1 个（0.2%）。

### 5.2 轮次与任务分布

以 `0919_exp7B_archB_step31k_20260919-142903` 为例（931 帧 / 16 轮）：

```
轮 1        5 帧    1.3s  insert_charger            ← 服务端预热（合成图）
轮 2-5    343 帧  834.4s  put_objects_into_basket   (4 轮)
轮 6-10   274 帧  373.0s  stack_bowls               (5 轮)
轮 11-13  202 帧  532.5s  stack_and_cover_blocks    (3 轮)
轮 14       1 帧    0.0s  fill_pen_holder           ← 异常：1 帧就结束
轮 15       5 帧   23.5s  fill_pen_holder
轮 16     101 帧  134.3s  stack_and_cover_blocks
────────────────────────────────────────────────
合计      931 帧                                       ✓ 与总帧数一致
```

按任务汇总：`put_objects_into_basket` 4 轮 343 帧 ｜ `stack_bowls` 5 轮 274 帧 ｜
`stack_and_cover_blocks` 4 轮 303 帧 ｜ `fill_pen_holder` 2 轮 6 帧 ｜ 预热 1 轮 5 帧

> **注意**：连续多轮常常是**同一个任务**（这里 `stack_bowls` 连跑 5 轮）。
> 所以「任务号变化」**不能**用来切分轮次 —— 它只是 `reset` 分界的真子集，会漏掉大半。

**三个可疑轮次**（建议排查）：

| 轮 | 现象 | 可疑 |
|---|---|---|
| 14 | 1 帧 / 0.0 s | 接任务后立刻 reset |
| 5 | 80 帧却 509 s | 帧数与别的轮相当，时长是 4–7 倍 |
| 13 | 33 帧却 245 s | 同上 |

这正是 v1 §6 里「卡死次数」那个**当时无记录**的指标 —— 现在 trace 已经能算出来了。

### 5.3 传输那 254 ms 的构成**尚未测出**

现在的 `timing` 只覆盖 `get_action` 内部的推理，**不覆盖 `update_obs`**。这 254 ms 里包含了客户端→服务端的往返（每 loop 16 次 `update_obs`，每次带 3 路图像）。

一个旁证：用**不做播放的 mock 客户端**跑同样的 loop 时，非推理开销是 **~900 ms**（16 次串行往返，约 56 ms/次）。真实客户端只有 254 ms，说明它的 `update_obs` 往返与 640 ms 播放**在时间上重叠**了。

**要确定这 254 ms 怎么来的、能不能压，需要在 `update_obs` 两侧加计时并记录图像载荷字节数。** 目前尚未做。

## 6. 口径与排除规则（读数字前必看）

**测量点**

| 指标 | 测量位置 | 含义 |
|---|---|---|
| `wall_ms` | `goai_xpolicylab.py` 的 `get_action_batch`，包住 `policy.infer()` | 整个推理调用 |
| `infer_ms` / `prepare_ms` / `denoise_ms` / `decode_ms` | `goai_sim_policy.py` 的 `infer()` 内部三段计时 | 模型内部拆分 |
| loop 间隔 | 两次相邻 `call` 事件的 `t` 之差 | 含播放与传输 |

`denoise_ms` 在 `.cpu()` 同步点之后取值，测的是**真实计算**而非 kernel 发射。

**已排除的数据**

1. **预热帧**（`env_id=7`）—— 服务端启动自检，重复同一张合成图，且无播放
2. **跨轮间隔**（`reset` 分界处）—— 那是轮次之间的空转（实测最长 **112.4 s**，中位约 1.2 s 的正常 loop 会被它完全压扁）
3. **中途停顿 ≥3 s** —— 仅在报告「正常 loop」时排除，§5.1 单独列出

**未做/未验证**

- 播放 640 ms 由协议标称值（40 ms/步 × 16）**推导**，非实测
- 传输 254 ms 未拆分（见 §5.3）
- `num_steps=20` 组含两个 run，`num_steps=50` 组含四个 run，任务构成不完全一致

## 8. 建议

1. **`num_steps` 20 → 10**：按线性模型推理可降到 ~192 ms，loop 降到 ~1086 ms。有自家消融背书（`technical_solution.md`：「ns40 收益饱和——维持 ah8/ns20」）。**改一行配置。**
2. **给 `update_obs` 加计时**：254 ms 是现在唯一没测过的部分，也是唯一可能藏着大块节省的地方。改动小。
3. **查 75 次中途停顿（§5.1）和三个异常轮次（§5.2）**：这些是评测失败的直接来源，比优化 10 ms 更值钱。
